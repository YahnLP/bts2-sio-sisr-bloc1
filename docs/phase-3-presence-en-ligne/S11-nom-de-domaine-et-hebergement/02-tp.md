## Contraintes

- Domaine et adresses **fictifs** (`bellevigne.example`, `203.0.113.x`) : tu n'interroges aucun vrai domaine.
- Les modifications de zone se font sur une **copie** ; tu vérifies avec `named-checkzone` **avant** de lancer le serveur.

## Partie A – Lire la zone (≈ 25 min)

Ouvre `bellevigne.example.db`.

1. Quelle est l'adresse du site `portail` ? Quel est son TTL, et celui des autres enregistrements ? ______________________
2. Où part le courrier adressé à `contact@bellevigne.example` ? ______________________
3. Que devient `www.bellevigne.example` quand on le résout ? ______________________
4. Que fait l'enregistrement TXT ? ______________________
5. La zone déclare deux serveurs de noms. Pourquoi deux ? ______________________

**J'anticipe.** Que répondrait le DNS pour `inconnu.bellevigne.example` ? ______________________

<details markdown="1">
<summary>Éléments de réponse</summary>

1. `203.0.113.30`, TTL **300 s** ; les autres enregistrements héritent du TTL par défaut, **3 600 s**.
2. Vers le serveur indiqué par le MX : `mail.bellevigne.example`, soit `203.0.113.40`.
3. C'est un alias : `www` renvoie vers `bellevigne.example`, soit `203.0.113.20`.
4. Il publie la politique SPF : seuls les serveurs de messagerie déclarés en MX sont autorisés à envoyer pour le domaine, les autres sont à rejeter.
5. **Redondance** : si l'un tombe, l'autre répond ; ils doivent être sur des machines et si possible des réseaux différents.

Pour le nom inconnu, la réponse attendue est une **absence de nom** (NXDOMAIN).

</details>

## Partie B – Vérifier et corriger (≈ 35 min)

1. Copie `zone-erronee.db`. Lance `named-checkzone bellevigne.example zone-erronee.db`.
2. Note **chaque** message, explique-le, corrige-le. L'outil peut ne signaler qu'une partie des défauts à la fois : recommence après chaque correction. Lis **toute** la sortie : un avertissement s'affiche parfois juste avant le mot `OK`.
3. Quand `named-checkzone` répond `OK`, relis la zone : y a-t-il un **défaut que l'outil ne détecte pas** parce qu'il est correct sur le plan syntaxique ? (Compare avec la zone de référence : le numéro de série.)

**J'anticipe.** Combien de défauts penses-tu trouver en lisant le fichier, avant de lancer l'outil ? ______

<details markdown="1">
<summary>Éléments de réponse</summary>

Trois défauts : un **CNAME** (`www`) qui coexiste avec un enregistrement A ; une **adresse invalide** (`203.0.113.300`, un nombre supérieur à 255) ; un **MX sans point final**, interprété comme `mail.bellevigne.example.bellevigne.example.` Le troisième est signalé comme un avertissement (nom sans adresse), pas comme une erreur. Le numéro de série n'est pas contrôlé : à chaque modification réelle, il faut l'augmenter soi-même.

</details>

## Partie C – Interroger (≈ 30 min)

1. Place `bellevigne.example.db` et `lance-dns-labo.sh` dans un dossier vide et lance `sh lance-dns-labo.sh` dans un premier terminal (serveur de laboratoire sur `127.0.0.1`, port 5353).
2. Dans un second terminal, avec `dig @127.0.0.1 -p 5353 +norecurse`, interroge : le MX de `bellevigne.example`, le A de `portail`, le CNAME de `www`, le TXT du domaine, et un nom qui n'existe pas.
3. Remplis : type demandé, `status`, valeur, TTL.

| Question | Status | Valeur | TTL |
|---|---|---|---|
| MX de `bellevigne.example` | | | |
| A de `portail.bellevigne.example` | | | |
| CNAME de `www.bellevigne.example` | | | |
| TXT de `bellevigne.example` | | | |
| A de `inconnu.bellevigne.example` | | | |

**J'anticipe.** Quel TTL verras-tu pour `portail` ? Pour le MX ? ______________________

<details markdown="1">
<summary>Éléments de réponse</summary>

À observer : TTL 300 pour `portail`, 3 600 pour les autres ; `NXDOMAIN` pour le nom inconnu.

## Partie D – Planifier une migration (≈ 20 min)

Le prestataire d'hébergement change. L'adresse de `portail` doit passer de `203.0.113.30` à `203.0.113.50`. Le TTL de `portail` est aujourd'hui de **3 600 s**. L'ouverture du nouveau serveur est prévue le vendredi à 8 h.

3. Écris le **plan en cinq étapes**, avec le jour et l'heure de chacune. ______________________
4. Que fais-tu du numéro de série, et que dois-tu garder actif jusqu'à la fin ? ______________________

## Partie E – Hébergement et certificat (≈ 45 min)

**E1. Comparatif sur trois ans.** Trois offres **fictives** :

| | A – Mutualisé | B – VPS | C – Infogérance |
|---|---|---|---|
| Prix annuel | 72 € | 15 € par mois | 1 200 € |
| Sauvegarde | non incluse, option 36 € par an | à gérer soi-même | incluse |
| Temps interne par an | 0 h | 20 h valorisées 40 € l'heure | 0 h |
| Localisation des données | non précisée | choix de la région | France |
| Engagement de disponibilité | aucun | 99,9 % | 99,9 % avec pénalité |
| Nom de domaine | 12 € par an dans les trois cas | | |

1. Calcule le **coût sur trois ans** de chaque offre, domaine compris. ______
2. Laquelle recommandes-tu pour un portail qui doit être fiable, en tenant compte des critères non financiers ? Justifie en trois lignes. ______
3. Quelles **trois questions** poses-tu à l'offre A avant de l'écarter ou de la retenir ? ______

**E2. Contrôler un certificat.** Crée un certificat de test (auto-signé, donc **sans valeur** pour un vrai site) :

```bash
openssl req -x509 -newkey rsa:2048 -nodes -keyout cle.pem -out certificat.pem -days 90 \
  -subj "/CN=portail.bellevigne.example" \
  -addext "subjectAltName=DNS:portail.bellevigne.example,DNS:www.bellevigne.example"
```

1. Affiche le sujet, les dates et les noms couverts : `openssl x509 -in certificat.pem -noout -subject -dates -ext subjectAltName`.
2. Teste si le certificat expire dans 30 jours, puis dans 100 jours, avec `openssl x509 -in certificat.pem -noout -checkend <secondes>` ; note le **code de retour** (`echo $?`).
3. Explique en trois phrases comment tu **superviserais** cette date dans une vraie infrastructure et pourquoi on automatise le renouvellement.

**J'anticipe.** Que renverra `-checkend` pour 100 jours (8 640 000 s) avec un certificat de 90 jours ? ______

<details markdown="1">
<summary>Éléments de réponse</summary>

Pour 30 jours (2 592 000 s) : « Certificate will not expire », code 0. Pour 100 jours : « Certificate will expire », code **1**. En production, on surveille la date de fin avec l'outil de supervision (alerte à 21 puis 7 jours, par exemple) et on automatise le renouvellement parce que les durées de validité raccourcissent et que les oublis coûtent une indisponibilité.

</details>
