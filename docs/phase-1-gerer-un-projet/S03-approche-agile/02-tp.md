## Contraintes

- Travail d'analyse et de rédaction ; le cas est **fictif** ; les raisonnements sont argumentés.

## Le cas : portail de réservation de salles de la mairie de Bellevigne

> **Situation (fictive).** La mairie de Bellevigne compte **35 agents** et six salles communales (salle des fêtes, salle du conseil, deux salles d'associations, gymnase, salle d'exposition). Les réservations se font par téléphone et dans un tableur partagé : **deux à trois doublons par mois**, des associations qui ne savent pas si une salle est libre, et un agent d'accueil qui passe plusieurs heures par semaine à répondre. La secrétaire générale souhaite un **portail de réservation en ligne**, ouvert aux associations et aux agents, avec un budget de **9 000 €** et une ouverture **dans quatre mois**. L'informatique est assurée par un technicien à mi-temps (toi, dans ce cas) et un prestataire pour l'hébergement.

## Partie A – Écrire des récits (≈ 40 min)

**1.** Écris **trois récits utilisateurs** complets (rôle, besoin, but) pour trois profils différents (association, agent d'accueil, secrétaire générale), chacun avec **trois critères d'acceptation** vérifiables.

**2.** Ce récit est-il bien écrit ? « En tant que développeur, je veux utiliser une base MariaDB. » ______________________

<details markdown="1">
<summary>Éléments de réponse</summary>

1. Exemples : association : voir les créneaux libres ; agent d'accueil : voir les réservations de la semaine et les imprimer ; secrétaire générale : connaître le taux d'occupation de chaque salle. Chaque critère est **vérifiable** (« affiche les 30 prochains jours », « un créneau réservé n'est plus proposé »).
2. Non : c'est une **solution technique**, pas un besoin d'utilisateur. Un récit décrit ce que l'utilisateur veut faire ; la base de données est un choix de réalisation.

</details>

## Partie B – Estimer et prioriser (≈ 45 min)

Voici huit récits. Attribue à chacun une priorité **MoSCoW** et vérifie les points proposés.

| N° | Récit | Points | MoSCoW |
|---|---|---:|---|
| R1 | Voir les créneaux libres d'une salle | 3 | |
| R2 | Réserver un créneau en ligne | 5 | |
| R3 | Annuler une réservation | 2 | |
| R4 | Recevoir un courriel de confirmation | 3 | |
| R5 | Gérer les salles (ajout, horaires) côté mairie | 5 | |
| R6 | Exporter les réservations vers un agenda | 3 | |
| R7 | Tableau de bord d'occupation pour la secrétaire générale | 8 | |
| R8 | Créer le compte d'une association | 5 | |

**Total du carnet :** ______ points.

**J'anticipe.** Quels récits sont des **Must** et pourquoi ? ______________________

<details markdown="1">
<summary>Éléments de réponse</summary>

Total : 3 + 5 + 2 + 3 + 5 + 3 + 8 + 5 = **34 points**.

Exemple : **Must** R1, R2, R8 (sans compte ni créneau visibles, aucune réservation possible), R5 (sans salles, rien à réserver) ; **Should** R3, R4 ; **Could** R6, R7. Accepter d'autres arbitrages justifiés par le besoin (la suppression de doublons exige R1 et R2).

</details>

## Partie C – Planifier les sprints (≈ 55 min)

La vélocité de l'équipe est de **10 points par sprint** (sprints de 3 semaines).

**1.** Combien de sprints faut-il pour tout livrer ? ______________________

**2.** Répartis les récits dans les sprints en respectant : les **Must d'abord**, les **dépendances** (on ne peut pas annuler une réservation qui n'existe pas encore : R3 après R2 ; R2 après R8 et R1), et **au plus 10 points par sprint**.

| Sprint | Récits | Points | Ce que l'on peut montrer à la revue |
|---|---|---:|---|
| 1 | | | |
| 2 | | | |
| 3 | | | |
| 4 | | | |

**Je comprends.** Après le sprint 2, la mairie souhaite ouvrir le portail aux associations. Est-ce possible ? Qu'est-ce qui manque encore ? ______________________

<details markdown="1">
<summary>Éléments de réponse</summary>

1. 34 / 10 = 3,4 donc **4 sprints** (12 semaines).
2. Exemple : sprint 1 : R5 (5) + R8 (5) = 10 → comptes et salles ; sprint 2 : R1 (3) + R2 (5) + R3 (2) = 10 → réserver et annuler ; sprint 3 : R4 (3) + R6 (3) = 6 ; sprint 4 : R7 (8). Total 34.
Un plan **valable** respecte les dépendances et la limite de 10 points ; plusieurs sont possibles.
Après le sprint 2, le portail **fonctionne pour réserver et annuler** : on peut ouvrir à un petit groupe d'associations pilotes. Il manque la confirmation par courriel (R4), l'export (R6) et le tableau de bord (R7) : ce sont des améliorations qui n'empêchent pas l'usage.

</details>

## Partie D – Prédictif ou agile ? (≈ 30 min, individuel)

Pour chaque situation, choisis **prédictif**, **agile** ou **mixte** et justifie en deux phrases :

| Situation | Choix |
|---|---|
| Remplacer les serveurs avant la fin du support du système, à date imposée et à périmètre identique | |
| Créer l'intranet d'une collectivité dont les agents ne savent pas encore ce qu'ils attendent | |
| Déployer 80 postes de travail dans 5 agences avec un budget fixe | |
| Traiter les demandes courantes du support | |

<details markdown="1">
<summary>Éléments de réponse</summary>

1. **Prédictif** : besoin stable, date imposée. 2. **Agile** : besoin évolutif, retours des agents. 3. **Prédictif** (planification et logistique) avec un suivi régulier ; on peut utiliser un Kanban. 4. **Kanban** (flux continu) plutôt que des sprints.

</details>
