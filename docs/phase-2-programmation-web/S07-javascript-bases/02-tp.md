## Partie A – Préparer la page et explorer la console (≈ 30 min)

1. Dans `salles.html`, ajoute **avant le tableau** un champ numérique `id="capacite-min"` (libellé « Capacité minimale », valeur 0) et, en fin de `body`, `<script src="salles.js"></script>`.
2. Ouvre la **console** et tape :

```js
const lignes = document.querySelectorAll("#tableau-salles tbody tr");
lignes.length
lignes[0].cells[1].textContent
typeof lignes[0].cells[1].textContent
```

**J'anticipe.** Que vaut `lignes.length` ? Quel est le type de la capacité lue dans la cellule ? ______________________

<details markdown="1">
<summary>Éléments de réponse</summary>

`lignes.length` vaut **6** (une ligne par salle). La capacité lue est du **texte** (`"string"`) : `"200"`, pas `200`. Il faut la convertir pour comparer.

</details>

## Partie B – Le filtre de capacité (≈ 50 min)

Complète `filtrerSalles()` : elle masque (classe `masque`) les salles dont la capacité est inférieure au minimum saisi. Branche-la à l'événement `input` du champ.

**Test.** Saisis 50 : quelles salles restent visibles ? ______________________

**Je comprends.** Que se passerait-il si tu comparais sans `Number(...)` : « 120 < 50 » ? ______________________

<details markdown="1">
<summary>Éléments de réponse</summary>

Avec 50, il reste : **salle des fêtes (200), gymnase (120), salle d'exposition (60)**. Sans conversion, la comparaison de textes est alphabétique : `"120" < "50"` est **vrai** (le caractère « 1 » précède « 5 ») : le gymnase serait masqué à tort.

</details>

## Partie C – La validation du formulaire (≈ 60 min)

Complète `validerFormulaire()` pour contrôler : nom non vide ; courriel au bon format ; date renseignée et **pas dans le passé** ; heures renseignées ; **fin après début**. À l'envoi, si la liste d'erreurs n'est pas vide, **bloque l'envoi** et affiche les messages dans `#message`.

**J'anticipe.** Comment compares-tu deux heures `"09:30"` et `"10:00"` de façon fiable ? ______________________

| Cas testé | Résultat attendu | Résultat obtenu |
|---|---|---|
| Formulaire vide | Envoi bloqué, messages « obligatoire » | |
| Fin avant début (10:00 → 09:00) | Envoi bloqué | |
| Date dans le passé | Envoi bloqué | |
| Courriel « pas-un-courriel » | Envoi bloqué | |
| Tout correct | Envoi accepté | |

<details markdown="1">
<summary>Éléments de réponse</summary>

Convertir chaque heure en **minutes depuis minuit** (`h * 60 + m`) puis comparer des **nombres** : 570 et 600. Comparer les textes marcherait ici (format fixe sur 2 chiffres) mais reste fragile ; la conversion est plus sûre.

</details>

## Partie D – Confort ou sécurité ? (≈ 30 min)

1. Dans les outils de développement, **supprime** le script (ou l'attribut `required`) et envoie le formulaire avec des champs vides : que se passe-t-il ? ______________________
2. Ouvre l'onglet **Réseau** : que contient la requête envoyée au serveur ? ______________________
3. Conclus en trois lignes : à quoi sert la validation côté navigateur, et pourquoi le serveur doit la refaire.

<details markdown="1">
<summary>Éléments de réponse</summary>

1. Sans script, le formulaire part tel quel : le navigateur ne **garantit** rien. 2. L'onglet Réseau montre les champs envoyés (méthode POST, données du formulaire) : n'importe qui peut forger la même requête. 3. La validation côté navigateur **améliore le confort** (message immédiat, moins d'allers-retours) ; elle ne protège pas : le **serveur contrôle toujours** (S09).

</details>
